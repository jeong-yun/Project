# 코드 검토 원칙 (오스마니 식)

이 저장소에서 코드를 새로 쓰거나 고칠 때 사람·AI 모두 따른다.
AI 도구는 저장소 맨 위의 [`AGENTS.md`](../../AGENTS.md)로 이 문서를 찾는다. `CLAUDE.md`·`GEMINI.md`는 그 파일을 가져오기만 한다.

## 점검 질문 5개

1. **본질과 목적**: 진짜 문제는 무엇인가? 더 단순한 해결책은 없는가?
2. **복잡성 제거**: 당장 없앨 수 있는 불필요한 20%는 무엇인가?
3. **성능과 비용**: 속도·메모리·확장성의 최악 시나리오는 무엇인가?
4. **유지보수성**: 한 달 뒤 나나 다른 사람이 1분 안에 이해할 수 있는가?
5. **미래 예측 방지**: 당장 필요 없는 기능으로 과도하게 만들고 있지 않은가?

## 원칙 4개

- **단순성 우선**: 더할 것이 없을 때가 아니라, 뺄 것이 없을 때 완성이다.
- **데이터 중심**: 추측하지 말고 측정한다.
- **작고 빠른 피드백**: 작게 바꾸고 바로 확인한다.
- **사용자 중심**: 사용자가 실제로 겪는 문제를 푼다.

## 이 저장소에서 적용하는 법

1. 코드를 새로 쓰거나 고친 뒤 위 점검 질문으로 스스로 검토한다.
2. 보고(진행보고·답변)에 '검토'를 몇 줄 남긴다.
   - 뺀 것
   - 단순하게 한 것
   - 남긴 복잡성과 그 까닭
3. 속도·건수·정확도처럼 측정이 필요한 주장은 dry-run·시험 수치로 보인다.
   - 이미 하는 관행과 같다: 건수 확인(호출 없음), 시험 폴더와 시험 화면(8790), 단위 시험, 고친 전후 비교.
4. 다른 사람이나 다른 AI에게 검토를 맡길 때는 아래 프롬프트를 붙여 쓴다.

## 검토 프롬프트 (복사해 쓰기)

```text
너는 Addy Osmani 스타일의 시니어 코드 리뷰어다. 아래 코드(또는 변경 내용)를 검토하라.

원칙: 단순성 우선(뺄 것이 없을 때 완성) · 데이터 중심(추측 말고 측정) · 작고 빠른 피드백 · 사용자 중심

검토 기준
1. 단순성: 더 단순한 해결책은 없는가? 지금 없앨 수 있는 불필요한 20%는 무엇인가?
2. 효율성·성능: 속도·메모리·확장성의 최악 시나리오는 무엇인가? 측정 없이 추측한 부분은 어디인가?
3. 가독성·유지보수성: 한 달 뒤 다른 사람이 1분 안에 이해할 수 있는가? 이름·구조·주석은 충분한가?
4. 핵심 가치: 사용자의 실제 문제를 푸는가? 당장 필요 없는 기능을 미리 만들지 않았는가?

출력 형식 (한국어)
1. 칭찬할 점
2. 제거·단순화할 부분 (가장 중요 - 지울 줄·바꿀 구조까지 구체적으로)
3. 리팩토링·개선 제안 (중요한 순서로)

[여기에 코드나 diff 를 붙인다]
```
