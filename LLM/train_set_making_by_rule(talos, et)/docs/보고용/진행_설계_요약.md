# 진행·설계 요약

진행 보고와 ML 피처 설계 문서를 줄인 것이다 (2026-10-14 ~ 10-30). 사용자 룰, 기존 학습 로그·기존 학습데이터(비공개)의 수치, 내부 환경 정보는 뺐다.

## 1. 무엇을 하나

Snort 룰(Cisco Talos, Proofpoint ET Open)을 **정답지**로 삼아, IPS/WAF 탐지 모델용 학습데이터(HTTP 공격·정상 요청)를 LLM 으로 만든다.

```
1.x 수집 → 파싱·선별·통합 → LLM 입력      3.x 생성 → 검토 → 증강      1.4 학습 로그(|||, 8필드)      4.x ML 피처·평가
                                         0.0 로컬 화면: 실행·진행률·신규 학습데이터·피처 확인
                                         5.x 기존 학습데이터와 비교 → 선별 → 버전(26 상반기 → 26 하반기 …) 확정
```

| 단계 | 하는 일 |
| --- | --- |
| 1.1 수집 | 룰 압축 파일을 매일 받는다 (버전 파일을 먼저 비교해 바뀐 것만) |
| 1.2 파싱 | 룰을 JSON 으로 정규화, HTTP 룰 판별, method 추출, 신규·변경·삭제 추출, 카테고리 선별, Talos↔ET 중복 제거 |
| 1.3 LLM 입력 | 생성에 필요한 필드만 (조건을 `conditions` 하나로 합침), 배치 분할 |
| 3.x 생성 | 생성 모델 → 코드 검사 → 검토 모델(pass/fix/drop, 거절하거나 안전 사유로 뺀 룰만 대체 모델로 다시) → 코드 재검사 → 증강 |
| 1.4 학습 로그 | IPS·WAF 로그(`시각|||출발IP|||포트|||목적IP|||포트|||method|||payload|||label`) + 줄별 label 파일 |
| 4.x 피처 | payload 의 확실한 공격 신호만 피처로, 묶음별 성능 비교 |
| 5.x 비교·버전 | 신규 학습데이터를 기존 학습데이터(기준 버전)와 비교해 샘플마다 등급(제거·A·B·C) → 사람이 선별 → 버전으로 확정하면 기존 + 신규 학습 파일·로그를 만든다 (10장) |

## 2. 룰 수집·선별

- 규모 (공개 룰, 2026-10): 수집 약 13만 개 → 서버 대상 공격 카테고리 선별·HTTP 룰만 약 2.2만 개 → 생성 대상 약 1.7만 개 (정보성·응답 방향 룰, 이미 충분한 룰 제외).
- **HTTP 판별**: HTTP 버퍼 수식어, pcre HTTP 플래그, `$HTTP_PORTS`, `service http` 외에 **원시 TCP 로 HTTP 요청을 검사하는 룰**(`content:"POST /api/... HTTP/"` 등)도 HTTP 로 본다. AI 서비스(비표준 포트)를 노리는 최신 룰을 놓치던 문제를 고쳐 약 100개를 더 살렸다.
- **선별**: `선별조건.md` 의 O/X 표로 관리하고, 표를 고치면 다음 실행 때 자동으로 다시 파싱한다. 카테고리와 상관없이 넣고 뺄 개별 룰 표도 있다.
- **중복 제거**: Talos 와 ET 에 같은 공격을 잡는 룰이 있으면 Talos 를 남긴다. 기준은 탐지 내용(content·pcre) 동일, 또는 같은 CVE + 같은 URI 경로·파라미터. content 값만 비교하는 느슨한 기준은 다른 룰을 묶는 오탐이 있어 쓰지 않았다.
- 파싱 규칙 버전을 두어, 파싱 로직을 고치면 같은 룰 버전이라도 자동으로 다시 파싱한다.

## 3. 라벨 정의

| 라벨 | 정의 |
| --- | --- |
| anomalies | 그 룰의 탐지 조건(content·정규식·부정 조건)을 **모두 만족** = 룰이 탐지 |
| normal | 같은 서비스·경로를 쓰는 **정상 사용자의 요청**으로, 조건을 하나 이상 어겨 룰이 탐지하지 않음 |

- "그 룰만 안 걸림" 은 정상의 충분조건이 아니다 (예: 공격 문자열을 다른 파라미터로 옮긴 **룰 우회 공격**). 그래서 normal 을 선별된 **전체 공격 룰**과 공격 흔적 피처로 다시 대조해, 다른 공격 룰이 탐지하거나 공격 흔적이 있으면 뺀다.
- **코드 검사(local_check)**: 샘플을 룰 조건과 기계적으로 대조한다. URI·본문은 URL 디코딩한 값도 본다. 위치 옵션(depth 등)은 근사라 검토 모델이 함께 본다. 다만 pcre 의 R(상대)은 바로 앞 content 가 끝난 자리부터 그 버퍼에서 본다 (2026-10-30, 14장). 룰로 판단할 수 없는 샘플(정규식 해석 불가)은 뺀다.
- method(공격 유형 이름)는 로그 형식 때문에 쓰지만 학습 정답은 label 이다.

## 4. 생성 파이프라인 (3.x)

- 호출 1회 = 룰 3개. LLM 은 룰마다 **씨앗** 샘플(공격 10·정상 5)만 만들고, 코드로 증강해 룰당 공격 50·정상 10 을 채운다. 증강은 룰 조건과 무관한 부분(Host, User-Agent, 부가 헤더, 끝 파라미터)만 바꾸고, 변형마다 코드 검사를 다시 통과한 것만 남긴다. LLM 에 50개를 직접 만들게 하면 비용이 10배 넘게 늘고 뒤로 갈수록 같은 샘플이 반복된다.
- 기존 학습데이터가 있으면 룰별 보유량을 계산해 **부족한 만큼만** 만든다 (충분한 룰은 제외, 조금 있는 룰은 기존 예시를 주고 비슷하지만 똑같지 않게).
- 단계별 결과를 폴더로 남겨 한 단계만 다시 돌릴 수 있고, 중간에 멈춰도 이어서 진행한다. 입력 날짜가 바뀌어도 **룰 내용 지문이 같은 룰은 다시 만들지 않는다**.
- 생성·검토를 한 번에 하나만 돌게 잠금을 두고(같은 요청에 API 비용이 두 번 들지 않게), 수집과는 동시에 돌 수 있게 했다 (생성은 시작할 때의 입력 날짜를 끝까지 쓰고, 수집은 새 입력을 임시 폴더에 다 쓴 뒤 한 번에 바꾼다).

## 5. 품질·현실성: 문제와 대책

| 문제 | 대책 |
| --- | --- |
| LLM 응답 JSON 이 여러 줄이거나 잘못된 이스케이프(`\x03`)로 깨져 룰 전체가 버려짐 | 객체 단위로 해석, 잘못된 이스케이프 복구 |
| 지시문의 출력 예시 개수(5개)를 그대로 따라 함 | 요청 메시지에 룰당 개수를 다시 명시 |
| 검토 의견: 공격이 교과서적(짧고 공격만 눈에 띔), User-Agent 가 실제 같지 않음 | 실제 공격 도구·익스플로잇 형태로 지시, 검토 기준에 현실성 추가, **헤더 현실화**(잘린 UA → 실제 문자열, 클라이언트 기본 헤더, Content-Length) |
| 생성 모델이 `%00%00…`, `..\..\…` 를 출력 한도까지 반복 (요청의 약 30%) | 긴 반복은 `{{REPEAT:문자열:횟수}}` 로 쓰게 하고 코드가 펼침, 잘린 룰만 다시 요청 |
| 생성 샘플의 약 30% 가 코드 검사 실패, 그 37% 가 **정규식 오해** (예: `<.+\/script` 는 보통의 `</script>` 와 불일치) | 정규식 구문 트리를 따라 **그 정규식에 실제로 맞는 예시**를 코드로 만들어 붙임 (정규식 조건의 99.3%) |
| 요청 줄 URI 에 공백을 그대로 씀 | 실제 클라이언트처럼 `%20` 으로 자동 수정 |
| 안전을 위해 쓰게 한 문서용 IP·`example.com` 이 생성 공격의 32.5% 에 있음 (실제 트래픽에는 없어 모델이 '공격 표시'로 배울 위험) | 학습 로그를 만들 때 샘플마다 다른 실제 같은 주소로 바꿈 (룰 판정이 달라지면 원래대로) |
| 생성 모델이 URI 에 글자 그대로 역슬래시+n 을 넣음 (`comment=ASCII(\nSELECT…`, `UPDATE\nSET`). 학습 로그는 줄바꿈도 두 글자 `\n` 으로 적으므로 다시 읽으면 줄바꿈이 되어 요청 줄이 잘리고 룰 조건이 안 맞음 → 전체 검증에서 '불일치' | 1.4 가 요청 줄의 이런 역슬래시를 `%5C` 로 적음 (`ASCII(%5CnSELECT`). 실제 클라이언트도 URL 의 역슬래시를 흔히 `%5C` 로 보내고, 룰 대조는 URL 디코딩 값도 보므로 판정은 그대로 |

- 검증: 생성 데이터 무작위 3,000줄을 다시 확인한 label 정합성 = 정합 88.3% · 정합(룰 기준: 이 룰의 고유 패턴으로만 공격) 11.7% · 불일치 0.
- 전체 검증 (2026-10-21, 하루치 학습 로그 190,226줄): 정합 87.8% · 정합(룰 기준) 12.2% · 불일치 110줄(0.06%). 110줄은 모두 위의 역슬래시+n 표기 문제였고(12개 룰, 생성 때 코드 검사는 통과), 1.4 수정 뒤 다시 확인하면 0.
- 남은 과제: 실제 공격 트래픽보다 인코딩이 많고, 본문(POST) 공격·자동화 도구의 짧은 탐색 요청·스캐너 UA 가 적다 (현실성 지시가 반대쪽으로 치우침). 증강 비율이 높아 공격 부분의 다양성은 씨앗이 정한다. 코드 검사는 근사이므로 실제 Snort 로 확인하는 단계가 남아 있다.

## 6. 속도

- 시간 대부분은 API 응답을 기다리는 시간이다 (요청 1개당 생성 약 1.5분 + 검토 약 1.5~2.7분).
- 요청을 동시에 보내고(속도 제한에 맞춰 자동 조절: 4개부터 늘리고 429 면 반으로), 생성된 요청부터 바로 검토한다.
- 실제: 요청 100개(룰 300개)가 하나씩이면 약 7시간 → 동시 생성 3·검토 4 로 약 1시간 → 동시 최대 생성 10·검토 12 로 약 28분 (준비 1.5분 + 생성·검토 24.6분 + 마무리 1.8분, 속도 제한 0건). 화면의 예상(약 24분)보다 늦어진 것은 생성 끝부분의 반복 루프 재시도 때문이다.
- '요청 수' 는 이번 실행에서 생성·검토할 수다 (이전 실행의 검토 대기분부터 처리하고 그만큼 덜 생성).
- **화면의 남은 시간**: 처음에는 검토 속도를 '단계 시작 → 지금까지 끝난 수' 로 재서, 검토가 첫 생성 결과를 기다린 시간이 들어가 실행 초반에 '4시간 남음'(실제 약 28분)처럼 나왔다. 지금은 최근 20개가 끝난 실제 간격으로 재고, 생성·검토를 함께 돌릴 때 검토는 '생성 끝 → 검토 끝' 시간 ÷ 동시 수로 잰다. 준비·마무리는 고정값 대신 지난 실행 3번의 단계별 실제 시간(증강은 요청 수에 비례)을 쓰고, 새 입력 날짜의 첫 실행(기존 로그 대조·요청 파일 만들기로 준비가 20분 넘게 걸림)은 그 진행 줄로 잰다.

## 7. ML 피처 설계 (4.x)

**원칙**

1. **payload 값만** 쓴다 (시각·IP·포트·method 는 쓰지 않음).
2. **표준 모델**(여러 환경 공용)이라 환경마다 달라지는 값은 쓰지 않는다 (헤더 수·길이, Cookie·Referer 유무, Host 등).
3. 공격 또는 정상을 **확실하게** 나타내는 신호만 쓴다. 모호한 것(문자 통계, 정보성 룰, 조건 일부 일치)은 뺀다.

| 묶음 | 접두어 | 수 | 내용 |
| --- | --- | ---: | --- |
| 공격 흔적 | `k_` | 10 | 디코딩한 payload 의 공격 유형별 키워드 수 (SQL, XSS, 명령, 경로 이동, 파일 포함, 템플릿·EL, XXE, 역직렬화, Shellshock, 민감 파일). 정상에도 나오는 형태는 뺌 (예: 명령 패턴은 `&` 가 아니라 `&&` 만) |
| 회피·이상 신호 | `k_` | 4 | 기호의 이중 URL 인코딩, `%u` 인코딩, 제어문자·NULL 바이트(파일 업로드 본문 제외), 스캐너·공격 도구 UA |
| 공격 룰 | `ra_` | 21 | 신뢰할 수 있는 공격 룰과 대조한 공격 유형 20개별 '모든 조건이 일치한 룰 수' + 합계 |
| 개별 룰 | `r_<룰>_` | 룰당 1 + 정규식 수 | 지정한 룰의 탐지 여부와 그 룰의 정규식 조건별 일치 |

- **모호한 룰 거르기**: 정상 데이터에도 자주 걸리는 공격 룰(정밀도 90% 미만)은 `ra_` 에서 뺀다.
- **2026-10-29 바뀜**: 위 `k_` 는 이제 라벨 검증·증강 교차 검사용 흔적으로만 쓴다. ML 신규 피처는 표준모델 피처가 못 잡는 갈래만 담은 `add_` 14개다 (13장). `ra_`·`r_` 는 라벨 누수 때문에 ML 피처로 쓰지 않고 라벨 검증용으로 둔다. 피처 성능 점검은 4.2(간단 모델) 대신 5.4 피처 실험으로 한다.
- **배운 점**
  - 구조 피처(헤더 수·Cookie·Referer·UA 종류)만으로도 같은 출처 데이터에서는 거의 완벽하게 맞히지만, 다른 출처 데이터로 평가하면 크게 떨어졌다. 모델이 "공격인가" 보다 "어느 출처인가" 를 배운 것이라 구조 피처를 뺐다.
  - 라벨을 룰로 정한 데이터에서는 룰 피처(`ra_`·`r_`)가 라벨과 거의 같다 (**라벨 누수**). 룰 단위로 나눠 평가하거나, 라벨을 독립적으로 정한 데이터로 평가한다. 같은 payload 는 학습·평가에 함께 두지 않는다.
  - 룰 하나의 정규식은 틀리지 않아도 공격의 아주 일부만 잡는다. 확실한 신호 여러 개를 합쳐 넓게 잡는 것이 ML 의 역할이다.
  - payload 한 건만으로는 공격이라 할 수 없는 경우(빈도 기반 탐지 등)는 원칙 3에 따라 잡지 않는 것이 맞다.

## 8. 화면 (0.0, 127.0.0.1 에서만)

진행 현황(생성 대상 룰 중 완료 %, 룰별 상태 플래그, 이번 실행의 % 막대·남은 시간·생성 품질), 생성·수집 실행(요청 수별 예상 시간·토큰 - 준비·마무리 포함, 수집 에이전트), 룰별 상태, 신규 학습 데이터(표: label 사유·검증 결과·label 정합성·탐지 피처, CSV 내려받기, 검증·수정·삭제), 피처 설명(마우스를 올리면 뜻·예·패턴), 기존 학습데이터와 비교(10장).

- 신규 학습 데이터는 표와 CSV 로만 본다. 로그 형식(`|||`) 파일은 버전을 확정할 때만 기존 학습데이터와 합쳐 만든다 (학습에 쓰는 로그가 하나의 확정본에서만 나오게).

## 9. 학습데이터 검증·수정 (2026-10-21)

**검증** = 학습 로그의 줄마다 label 이 증거와 맞는지(정합 / 정합(룰 기준) / 확인 필요 / 불일치)와 켜지는 탐지 피처를 정한다. 줄마다 ① 공격 흔적 14종 ② 신뢰할 수 있는 공격 룰 약 1.6만 개와 대조 ③ 그 줄을 만든 룰의 조건을 다시 확인 ④ normal 이면 다른 공격 룰·흔적과 교차 검사.

| 문제 | 대책 |
| --- | --- |
| 17만 줄 검증이 약 90분 (장비마다) | 줄마다 '최신 입력 날짜 폴더'를 두 번씩 새로 찾던 것(한 번 8ms)을 없앰 → 줄당 23ms → 8ms. 남은 시간의 3/4 은 공격 룰 대조 |
| IPS·WAF 로그는 같은 샘플(method·포트만 다름)인데 장비마다 처음부터 검증 | 다른 장비의 결과를 그대로 씀 (IPS 검증 중이면 WAF 는 끝나기를 기다렸다 이어받음) → WAF 1~2분 |
| 새 생성 실행으로 로그가 다시 만들어지면 전체를 다시 검증 | 줄별 결과에 **줄 내용 지문**(payload·label·룰 id·생성/검토 정보의 SHA-1)을 적어, '검증 안 한 데이터만 검증' 은 이미 확인한 줄을 찾아 그대로 쓰고 새 줄만 확인. '전체 검증' 은 지금 룰로 전부 |
| 매일 수집으로 룰 입력 날짜가 바뀜 | 예전 룰로 확인한 결과도 그대로 쓰고, 이전 룰 기준 줄 수를 화면에 표시 (최신 룰로 다시 보려면 전체 검증) |
| 오래 걸리는 검증을 멈출 수 없고 남은 시간을 모름 | 중지 버튼 (확인한 줄은 저장해 이어서), 검증 중에 로그가 다시 만들어지면 스스로 멈추고 저장. 남은 시간 = 새로 확인할 줄 수(시작할 때 지문으로 셈) × 최근 1분 속도 |
| 불일치 줄을 고칠 방법이 없음 | 화면에서 줄마다 **수정**(label·payload, '다시 확인' 으로 저장 전에 검증)·**삭제**·불일치 일괄 삭제. 저장은 샘플 지문(룰 id·샘플 번호·LLM 출력)을 열쇠로 하는 `edits.json`, 1.4 가 학습 로그를 만들 때마다 적용 (IPS·WAF 함께). LLM 출력은 그대로라 되돌리면 원래 샘플 |

- 시험: 데이터 복사본에서 처음 검증·중지·이어서·로그 변경·예전 형식·룰 입력 변경 7가지와 수정·삭제·반영·되돌리기를 확인 (되돌린 뒤 원래 로그와 한 글자도 다르지 않음).
- **배운 점**: 검증의 '불일치' 는 데이터가 아니라 **로그 표기(직렬화)** 의 모호함에서 나올 수 있다. 줄을 지우기 전에 원인을 먼저 보고, 자동으로 고칠 수 있는 것은 변환 단계(1.4)에서 고친다. 사람이 고치는 것은 원본(LLM 출력)을 바꾸지 않고 덧씌우기로 남겨 되돌릴 수 있게 한다.

## 10. 기존 학습데이터와 비교·버전 (2026-10-22)

생성한 학습데이터를 전부 기존 학습데이터에 넣으면 이미 학습된 패턴(예: 같은 SQLi 변형의 반복)이 쏠리고 중복이 섞인다. **기존 데이터에 없는 공격·부족한 데이터만** 골라 버전으로 쌓는다.

```
신규 학습데이터 → ① 비교: 기준 버전과 비교해 샘플마다 등급 → ② 선별: 규칙 + 사람이 룰·공격 유형 단위로 조정
               → ③ 버전 확정: 기존 + 신규 학습 파일(CSV)·로그 → 다음 버전은 이 버전을 기준으로 ①부터
```

| 등급 (앞이 우선) | 뜻 | 선별 기본값 |
| --- | --- | --- |
| 제거 | 신규 내부 중복(숫자만 다른 것 포함) 또는 기준 데이터에 같은 payload | 뺌 |
| A 부족한 데이터 | 기준 데이터로 학습한 모델(RF·LGBM) 중 하나라도 틀림 (못 잡는 공격, 공격으로 보는 정상) | 전부 |
| B 새 패턴 | 피처 패턴(피처마다 켜졌는지의 조합)이 기준 데이터에 없음, 모델은 맞힘 | 패턴당 20 |
| C 이미 학습됨 | 패턴도 있고 모델도 맞힘 | 패턴당 20 (분포 유지) |

| 문제 | 대책 |
| --- | --- |
| 분석 코드와 학습데이터 생성이 따로 있어 화면에서 받은 CSV 를 손으로 옮김 | 분석을 5.x 로 옮겨 화면 6 에서 08_dataset 을 바로 읽어 비교 (IPS·WAF, 여러 날짜, 화면에서 고친 샘플 포함). 옮긴 코드로 같은 입력의 기존 분석 결과(등급 수·기준 모델 탐지율·선별 수)가 같음을 확인 |
| 표준모델 피처 코드는 비공개 | 피처 이름·정규식을 코드에 적지 않고 표준모델 피처 파일에서 읽음 (공개본은 위치만 넣으면 됨). 열 단위로 다시 구현한 계산이 원본 함수와 같은지(차이 0) 확인 |
| 새 룰이 계속 들어오는데 매번 전체를 다시 비교 | 피처를 payload 지문으로 캐시해 새 샘플만 계산. 확정한 버전은 비교한 샘플 지문을 남겨 다음 비교에서 뺌 |
| 사람이 본 수와 실제로 넣는 샘플이 다를 위험 | 미리 보기와 확정이 같은 선별 계산을 쓰고, 담을 때의 비교 스냅숏과 학습데이터 상태가 확정할 때와 같아야만 내보냄 |

| 나중에 결합 학습을 평가할 때 학습·평가 데이터가 섞임 | rule_id 지문으로 30% 를 평가용(holdout)으로 표시 (새 룰이 와도 기존 룰의 분할은 그대로) |

- **배운 점**: 기존 데이터로 학습한 모델은 처음 보는 정상 요청을 많이 공격으로 본다 (기존 정상이 소수 사이트에 몰려 있음). 신규 데이터의 가치는 공격보다 **정상(오탐을 바로잡는 데이터)** 에서 크고, A 등급의 절반 가까이가 정상이다.

## 11. 보류 데이터·로그 구분자·진행률·정규식 시간 제한 (2026-10-22 오후 ~ 10-26)

| 문제 | 대책 |
| --- | --- |
| 담당관 판단을 기다리는 데이터('정합 (룰 기준)' 공격, python-requests UA 정상)를 따로 볼 수 없음 | 4. 에 '보류 대상' 필터, 6. 에 보류 대상 수(등급별, 옵션을 켜면 빠지는 수)와 '보류 데이터만 보기'. python-requests 정상은 payload 에 공격이 없으면 정상이라는 원칙대로 넣기로 함 (기존 데이터에는 이 UA 의 정상이 없어 기존 모델이 UA 만 보고 공격으로 판단하던 것을 바로잡는 데이터) |
| payload 가 `\|` 로 끝나면 로그가 `…\|\|\|\|anomalies` 가 되어 앞에서 나누면 label 이 `\|anomalies` 로 읽힘 | 읽는 쪽(화면·5.x)은 label 을 마지막 `\|\|\|` 뒤로 읽음. 1.4 는 이런 payload 끝에 줄바꿈 하나를 붙임 (본문이면 Content-Length +1, 룰 판정이 달라지면 제외). 다른 파서가 확정 로그를 앞에서 나눠도 맞게 읽힘 |

| API 한도에 여유가 있는데 동시 요청 최대가 낮음 | 최대 생성 10 → 15, 검토 12 → 20 (속도 제한이 오면 자동으로 줄임) |

- **배운 점**: 룰의 정규식을 학습데이터 검사에 그대로 쓰면, 탐지 엔진처럼 검사 한도(시간 제한)를 두어야 한다. 그리고 생성·비교·검증·실험처럼 계산이 많은 작업을 한 PC 에서 겹쳐 돌리면 서로 크게 느려지므로, 무거운 작업은 생성의 계산 단계와 겹치지 않게 한다.

## 12. 검토 모델의 안전 거부·Claude CLI 검토·검증 보완 (2026-10-26)

| 문제 | 대책 |

| IPS·WAF 에 같은 신규 학습데이터를 넣어야 함 | 등급은 장비마다 매기고, 선별할 때 샘플 지문으로 짝지어 합친 등급(어느 장비든 A 면 A …)으로 한 목록을 골라 두 장비에 같은 샘플로 확정한다 |

- **배운 점**
  - 검토 모델의 '안전' 판단은 모델마다 크게 다르다. 같은 요청에서 한 모델은 공격 샘플의 절반 가까이를 뺐고, 다른 모델은 하나도 빼지 않았다.

## 14. 상대 정규식 검사·큰 반복·지정 룰 다시 만들기·룰 기준 재확인 (2026-10-30)

| 문제 | 대책 |
| --- | --- |
| Snort pcre 의 `R`(상대) 플래그는 바로 앞 content 가 끝난 자리부터 검사하고 `^` 도 그 자리인데, 코드 검사는 버퍼 처음부터 봤다. 그래서 룰대로 만든 공격(`content:"id="` 뒤 `/^(?:SELECT\|UNION…)/R` 에 맞춘 `id=UNION SELECT …`)을 '조건 불일치'로 뺐다 (R 정규식이 든 공개 룰 약 530개) | 파싱이 R 정규식 바로 앞 content 를 `after` 로 기록해 LLM 입력 조건에 넣고 (예전 입력도 옮김, 룰 내용 지문은 그대로), 코드 검사는 기준 content 가 나온 자리마다 바로 뒤부터 그 content 의 버퍼(예: URI)에서만 본다 (Snort 3·Suricata 와 같은 범위). 생성·검토 지시문과 정규식 예시도 'content 바로 뒤' 모양으로 보여 준다. 화면 4 검증은 판정 규칙 판을 올려 R 룰의 줄만 다시 확인한다 |
| 이미 끝난 결과에도 같은 이유로 빠진 공격이 남음 | LLM 을 다시 부르지 않고 저장된 검토 판정으로 다시 합친다 (예전 검사로 다시 돌린 결과가 저장된 것과 똑같은 요청만). 공격 씨앗 약 1,900개를 되살려 증강까지 약 9,300개를 붙였다 (기존 샘플·샘플 지문은 그대로, 다른 룰의 학습 로그 변화 0). 새 검사로 룰에 걸리는 정상 46개는 지우지 않고 수정·삭제 기록으로 뺐다. 공격이 0 이던 R 룰 약 180개가 공격 샘플을 얻었다 |
| 정규식이 multipart 파트·빈 줄을 100번 넘게 반복해야 맞는 룰(`(…){100,}`)은 모델이 그만큼 넣지 않거나 '과도한 요청'으로 뺌 | 실제 로그가 payload 를 자르지 않는 것을 확인한 뒤, 모델은 파트·빈 줄을 1~3개만 넣고 코드가 채운다: 그룹 반복 20번 이상이면 맞는 파트를 복사해 n+5 개로 (3만 자가 넘으면 파트 내용을 줄임), Content-Length 를 맞추고 코드 검사가 맞을 때만 바꾼다 |
| 완료 상태인데 공격 샘플이 0 인 룰(약 410개)을 바뀐 검사·지시문으로 다시 만들 방법이 없음 (완료 룰은 요청을 다시 만들지 않음) | '지정 룰 다시 만들기': 룰 목록을 주면 완료 상태여도 새 요청(`pick_…`)으로 만들고 그 요청만 생성·검토한다 (다른 검토 대기분은 그대로). 다시 만들어도 코드 검사를 못 넘는 룰(위치가 붙은 부정 content 등 근사의 한계)은 빼고 약 320개·요청 약 110개 - 실행은 승인 뒤 |
| 코드 검증의 '정합 (룰 기준)'(룰 조건은 모두 맞지만 범용 공격 흔적이 없어 룰의 고유 패턴으로만 공격으로 본 줄, 약 18만 줄)은 학습에 쓸 만한 공격인지 코드로는 알 수 없음 | 화면 4 'LLM 재확인'의 대상에 넣었다: 룰마다 LLM 원본 샘플 몇 개(기본 3, 같은 조건이면 같은 줄)만 표본으로 묻는다. 지시문은 대상마다 나눠, '요청만 보고 같은 경로·파라미터의 정상 요청과 구분할 수 없으면 학습에 부적합'으로 판정하게 했다. 룰별 요약(부적합 비율)에서 고른 룰은 화면 6 선별의 '룰 빼기'로 넘긴다 (담기는 사람이). 시작 전에 요청 수·비용·시간을 보이고, 구독 모델이면 사용량 경고를 띄운다 |
| 화면을 켠 직후 피처 화면을 처음 열면 가끔 'Failed to fetch' | 보조 모듈을 처음 읽는 동안 두 번째 요청이 반쯤 찬 표를 봄 (경합) → 잠금 안에서 다 읽은 뒤 한꺼번에 넣음 |

- **배운 점**
  - 룰 문법의 상대 위치(R 등)를 근사로 무시하면, 룰대로 만든 정답 샘플이 거꾸로 '불일치'가 된다. 근사 검사가 무엇을 빼고 보는지 적어 두고, 빠진 샘플이 몰리는 룰 모양을 주기적으로 센다.
  - 검사 규칙을 고친 뒤에는 LLM 을 다시 부르기보다 저장한 판정으로 다시 합치는 것이 싸고 재현할 수 있다. 다만 예전 규칙으로 다시 돌린 결과가 저장된 것과 똑같은 것만 고친다.
  - 룰 기준 라벨은 '탐지된다'는 뜻일 뿐 '학습에 좋은 공격'은 아니다. 공격 내용 없이 위치만으로 탐지하는 룰의 샘플은 정상과 구분되지 않아, 룰 단위로 걸러 낼 근거가 필요하다.

## 15. 다음 단계

- 남은 생성 요청을 마치고, 공격 샘플이 0 인 룰의 지정 룰 다시 만들기(승인 뒤) → 화면 4 검증(새 판정 규칙) → LLM 재확인('불일치' 전부, '정합 (룰 기준)' 룰당 표본) → 비교 → 선별 확인(부적합이 많은 룰 빼기 포함) → 26 하반기 확정
- 피처 개선은 확정본(고정된 데이터)으로 실험해 정함 → 결합 학습·평가 (기준 단독 vs 기준 + 신규, holdout 룰로 평가). 그 전까지 등급을 매기는 피처는 바꾸지 않음 (반기 안에서 선별 기준을 같게)
- 실제 Snort(WSL 또는 Docker)로 생성 샘플이 그 룰에 실제로 탐지되는지 확인 (코드 검사의 남은 근사: 위치가 붙은 부정 content, 판단할 수 없는 정규식)
- 공격 형태 분포를 실제 트래픽에 맞추기 (짧은 자동화 요청, 본문 공격, 인코딩 비율)
- 검증의 공격 룰 대조(시간의 3/4)를 여러 프로세스로 나누기
