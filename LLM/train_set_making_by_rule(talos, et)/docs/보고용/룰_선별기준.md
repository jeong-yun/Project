# 룰 선별 기준과 근거

작성: 2026-10-15 (사용자 지정 조건 반영) · 대상: Talos 스냅샷 29200 (md5 591c47da…), ET Open 버전 11311

**결론:** Talos 9개 카테고리 8,234개와 ET 7개 카테고리 13,952개를 합친 뒤, 양쪽에 같은 룰 437개를 빼서 **통합 HTTP 룰 21,749개**를 만들었다. 그중 95%(20,584개)가 HTTP 요청 룰이다.

- **선별 조건의 원본: [`선별조건.md`](../코드참조/선별조건.md)** — 표의 O/X를 고치면 다음 실행 때 자동으로 다시 파싱된다.
- 이 문서는 조건을 정한 **근거**를 기록한 것이다. 조건을 바꿔도 이 문서는 자동으로 바뀌지 않는다.
- 실행할 때마다 자동으로 만드는 카테고리별 수치: `04_integrated/<날짜>/selection_report.md`
- 선택한 카테고리 중에서도 **HTTP 룰만** `03_processed/`와 `04_integrated/`에 들어간다.

## 2. ET 선별

ET는 룰 파일이 하나뿐이라 msg의 카테고리(`ET WEB_SERVER ...`의 `WEB_SERVER`)로 나눈다. `GPL ...`로 시작하는 옛 커뮤니티 룰도 같은 방식으로 분류한다.

**판단 방법:** Talos 선택(서버 대상 공격 + SQL)과 성격이 같은지를 보고, **룰의 방향**으로 검증했다. 서버 공격 룰은 외부에서 내부 서버로 가는 요청(`→ $HOME_NET / $HTTP_SERVERS`)이어야 한다.

### 주의할 점

- **INFO (사용자 지정 선택)**: 4,230개 중 90%(3,813개)가 요청 룰이지만, 서버행 요청은 88개(2%)뿐이다. 대부분은 내부에서 외부로 나가는 정보성 룰이다(동적 DNS 접속, 의심 TLD 다운로드, PUA User-Agent). XXE, 웹셸 요청 같은 서버 공격 룰도 포함된다. 공격 페이로드 생성 단계에서 결과 품질을 확인하는 것이 좋다.
- **POLICY**: 서버행 요청은 10%뿐이고 대부분 내부에서 외부로 나가는 요청이다. 앱 사용 탐지 성격이다.
- **SQL**: ET SQL 카테고리는 HTTP 룰이 1개뿐이지만, ET의 SQL 인젝션 룰은 WEB_SPECIFIC_APPS에 4,228개 있으므로 SQL 인젝션 데이터는 충분하다.

## 3. Talos ↔ ET 중복 제거

두 소스에는 같은 공격을 탐지하는 룰이 함께 들어 있다. 통합 결과에서는 **Talos 룰을 남기고 같은 ET 룰 437개를 뺐다.** 소스별 결과(`03_processed/`)는 그대로 둔다. 설정은 [`선별조건.md`](../코드참조/선별조건.md)의 `## 중복 제거` 표에서 바꿀 수 있다.

**'같은 룰' 판단 기준:** SID 번호는 소스마다 달라서 쓸 수 없으므로 탐지 내용으로 비교했다.

| 기준 | 제거 수 | 내용 | 예 |
| --- | ---: | --- | --- |
| 1. 탐지 내용 동일 | 77 | content(검사 위치·값, 대소문자 무시)와 pcre가 모두 같음 | ET `GPL WEB_SERVER global.asa access` = Talos `SERVER-IIS global.asa access` |
| 2. 같은 CVE + 같은 경로 | 360 | CVE가 같고, URI 검사 값 중 경로·파라미터가 하나 이상 같음 | ET `Palo Alto Expedition SQL Injection` = Talos `Palo Alto Networks Expedition SQL injection attempt` (같은 `/bin/.../checkpoint.php`) |

제거된 ET 룰의 카테고리: WEB_SPECIFIC_APPS 243, EXPLOIT 124, WEB_SERVER 63, SCAN 5, POLICY 1, INFO 1.

**판단 근거 (비판적 검토)**
- **기준 1**은 대부분 ET의 GPL 룰이다. 원래 Snort(VRT) 룰을 ET가 그대로 가져온 것이라 명확한 중복이다.
- **기준 2**에는 ET가 한 취약점을 여러 변형(DELETE, UNION SELECT, INSERT 등)으로 나눈 룰도 포함된다. 예를 들어 ASPMForum은 Talos 1개에 ET 여러 개가 대응한다. 같은 취약점의 같은 경로이므로 중복으로 봤다.
- **쓰지 않은 기준**: content 값만 비교하는 느슨한 기준은 "ET SCAN HTTP GET invalid method case"와 "Oracle Enterprise Manager overflow"처럼 서로 다른 룰을 묶어서 뺐다.
- **기준 2의 오탐 방지**: 겹치는 값이 `select`, `union` 같은 SQL 키워드이거나 `/../` 같은 기호뿐이면 인정하지 않는다. 처음 검토에서 Neocrome LDU SQLi가 Talos의 범용 SQLi 룰과 키워드 `select`로 묶이는 오탐이 있어서 이 조건을 넣었다.
- **애매한 사례**: ET "Apache Tomcat TOCTOU"와 Talos "JSP webshell upload attempt"(범용)가 같은 CVE와 `.jsp`로 묶였다. 같은 CVE를 탐지하므로 중복으로 허용했다. 전체 쌍은 `duplicates.json`에서 검토할 수 있다.
- **Talos를 남긴 이유**: 선별 기준을 Talos 카테고리로 먼저 정했고, GPL 룰의 원본도 Snort/Talos 쪽이다. 다만 ET의 변형 룰이 페이로드 키워드(UNION SELECT 등)를 더 구체적으로 담고 있으므로, 페이로드 다양성이 중요하면 `남길 소스`를 `et`로 바꾸는 것도 고려할 수 있다.

## 5. 조건 바꾸는 방법

1. [`선별조건.md`](../코드참조/선별조건.md)의 표에서 **선택** 열을 `O` 또는 `X`로 고친다. 새 카테고리는 줄을 추가한다.
2. 평소처럼 실행한다. 조건이 바뀐 것을 감지해 자동으로 다시 파싱한다.
   ```powershell
   python 1_0_run_daily.py
   ```
3. `04_integrated/<날짜>/selection_report.md`에서 결과를 확인한다.

동작 방식:
- **O → X로 바꾼 카테고리**: 결과에서 빠진다. "삭제"로 잡히지 않는다.
- **X → O로 바꾼 카테고리**: 결과에 들어가고, `llm_queue`에 `change: "selection_added"`로 들어간다. LLM 입력에서 빠지지 않는다.
- **이유 문구만 바꾼 경우**: 다시 파싱하지 않는다. 보고서에는 다음 파싱 때 반영된다.
- **O/X가 아닌 값을 넣은 경우**: 파싱을 중단하고 `logs/parse.log`에 줄 번호와 함께 오류를 남긴다. 기존 결과는 그대로 둔다.
- **중복 제거 설정을 바꾼 경우** (`## 중복 제거` 표): 다시 파싱하지 않고 통합 결과(`04_integrated/`)만 다시 만든다.

## 6. 2026-10-16 보완

- **개별 룰**: `선별조건.md`의 `## 개별 룰` 표로 카테고리와 상관없이 특정 룰을 넣거나 뺄 수 있다. 첫 항목은 `talos:1:66203`(Langflow Public Flow 명령 실행, CVE-2026-33017, Talos `policy-other`)이다.
- **HTTP 판별 보완**: HTTP 키워드 없이 원시 TCP로 HTTP 요청을 검사하는 룰(`POST /... HTTP/`, `^(GET|POST)` 정규식 등)도 HTTP 룰로 본다. 선택 카테고리에서 약 100개가 추가됐다 (ET 14,013 / Talos 8,274, 중복 제거 후 통합 21,848).
