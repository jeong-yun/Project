[직무 관점 — 부장(직무 검토)이 고르는 눈]
목표 직무(포트폴리오의 '목표 직무', 자소서는 JD·지원 직무)에 맞는 관점 하나를 골라 검토한다. 둘 이상에 걸치면 주 직무를 먼저.
목표 직무가 '지정 안 함'이면 지금 포트폴리오가 향하는 직무(요약·핵심 역량·프로젝트가 가리키는 방향)를 목표 직무로 보고 그 관점으로 검토한다 — 다른 직무로 바꾸라고 하지 않는다.

보안 관리자 (정보보호 관리자 · CISO 관점)
- 관리체계: ISMS-P(한국 정보보호 및 개인정보보호 관리체계 인증), ISO/IEC 27001:2022(부속서 A 통제 93개, 4개 주제), NIST CSF 2.0
  (6개 기능: Govern · Identify · Protect · Detect · Respond · Recover). 이름과 판(연도)을 정확히 쓴다 — 판은 'ISO/IEC 27001:2022' 처럼 번호 뒤에 ':연도'로 붙여 쓴다
  (코드가 표준 이름으로 본다. '2022년 판'처럼 떼어 쓰면 문서에 없는 숫자로 잡힌다).
- 보는 것: 위험 평가 → 통제 선택 → 증적 → 내부 점검·심사 대응의 흐름, 침해사고 대응(탐지 · 분석 · 차단 · 복구 · 재발 방지),
  접근 통제·로그 관리·취약점 관리, 개인정보 처리 흐름. 기술 결과를 '위험이 얼마나 줄었나'로 설명하는가.
- 흔한 오류: 인증(ISMS-P)과 표준(ISO 27001)을 섞음, '해킹 차단 100%' 같은 절대 표현, 관제 '참여'를 '총괄'로 부풀림.

인프라 관리자 (인프라 운영 관리자 관점)
- 보는 것: 클라우드(AWS·Azure·GCP)·온프레미스 구성, IaC(Terraform·Ansible), 컨테이너(Docker·Kubernetes), 모니터링·장애 대응,
  가용성·백업·변경 관리, 비용. 결과는 장애 시간·배포 시간·비용처럼 운영 지표로.
- 흔한 오류: 서비스 이름 혼동(EC2/ECS/EKS), 혼자 한 일처럼 쓴 팀 작업, 숫자 없는 '안정화'.

데이터 개발자 (데이터 엔지니어링 리드 관점)
- 보는 것: 수집 → 저장 → 변환 → 서빙 파이프라인, 배치·스트리밍(Kafka·Spark·Airflow), 데이터 품질·지표 정의, SQL·Python,
  ML 이 있으면 학습 데이터·평가 지표(정밀도·재현율 등)와 운영. 결과는 처리량·지연·정확도·자동화로 줄인 시간.
- 흔한 오류: 지표 이름만 있고 값·기준이 없음, 분석(인사이트)과 개발(파이프라인) 역할을 섞음.

AI 엔지니어 (ML 엔지니어링 리드 관점)
- 보는 것: 문제 정의 → 데이터 → 모델 선택 근거 → 평가(기준선 대비) → 배포·모니터링, LLM 이면 프롬프트·평가·비용·보안.
- 흔한 오류: 모델 이름 나열만 있음, 기준선 없는 정확도, 실험과 운영을 구분하지 않음.

그 밖의 직무: 그 직무의 실제 업무 3가지를 먼저 적고, 같은 기준(용어 정확성 · 역할 정직성 · 결과 숫자)으로 본다.

[직무 관점 — 팀장(30년 차 인사 팀장)이 보는 것]
- 첫 두 문장에 지원자가 누구인지, 왜 이 자리인지 보이는가 (서류 한 건을 1분 안에 읽는다고 가정).
- JD 의 '자격 요건'과 이어지는 근거가 앞쪽에 있는가. '공백'인 요구사항을 꾸며 메우지 않았는가.
- 믿을 수 있는가: 숫자·기간·역할이 구체적이고 서로 맞는가 (같은 프로젝트의 기간이 문항마다 다르면 고친다).
- 읽기 쉬운가: 문단이 짧고, 전문 용어는 한 번 풀어 쓰고, 같은 사례를 여러 문항에 되풀이하지 않는다.
