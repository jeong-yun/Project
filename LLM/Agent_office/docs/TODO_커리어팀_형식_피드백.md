## 수정안 (팀장 정리본 — 가명 처리)

### 1. 형식 우선순위 (portfolio · recommend_update)
- 사람이 '기존 문서 형식과 유사하게'라고 요청하면 그 형식이 표준 형식(요약·핵심 역량·카드 다섯 줄·직무 강점)보다 우선한다.
- 출력은 요청한 형식마다 하나씩 만든다. (예: Word용 = 기존 Word 경력서 표 형식, md용 = 기존 md 경력서 형식)
- 표준 형식은 '추가 요청이 없을 때'의 기본값이다. 절 제목·카드 항목을 확인하는 코드 검사도 이 조건을 따른다.
- 바뀌지 않은 표·항목도 빠짐없이 전부 출력한다. '나머지는 원문 그대로 둡니다' 식으로 생략하지 않는다.
- '부록' 형태로 요청 형식을 뒤에 미루지 않는다.

### 2. 구분(섹션) 유지
- 원문의 큰 구분(예: 대학원 · 군 · 회사 · 개인 프로젝트)과 그 순서를 지킨다.
- '목표 직무와 가까운 것을 앞에' 규칙은 같은 구분 안에서만 적용한다.
- 회사 업무와 개인 프로젝트를 섞지 않는다.
- 원문의 분류가 모호하면 옮기기 전에 사람에게 묻는다. (예: 개인 작업이 '업무 명'으로 회사 표 사이에 있음)

### 3. 날짜·기간 표기
- 같은 날짜를 표기만 바꾸는 것(YYYY-MM-DD → YY.MM)은 허용한다. 이때 원래 표기를 evidence quote 에 남긴다.
  → 코드 검사도 날짜 정규화(2026-06-01 ≒ 26.06)를 '문서에 없는 숫자'로 보지 않도록 고친다.
- '~ 현재'는 '~ 진행 중'으로 바꿔도 된다. 끝난 날짜가 없는 일은 '진행 중'으로 적는다.
- 개월 수 '(N개월)'는 원문에 있을 때만 쓴다. (새로 계산하면 [확인 필요] — 위 표 참고)
- 한 문서 안의 날짜 형식은 하나로 통일한다.

### 4. 그림·흐름도
- 텍스트 추출본에 '흐름도'·'그림' 표시만 남은 자리는 조용히 빼지 않는다. `[흐름도 — 기존 그림 유지]` 자리를 남기고 needs_check 에 적는다.
- 사람이 mermaid 등 그림 원본 코드를 주면 그대로 재사용한다.
- 새 흐름도는 mermaid 로 같은 스타일(flowchart LR · subgraph · 번호 노드 · `<br/>•` 목록)로 그린다. 노드의 모든 문구와 숫자는 본문과 같은 사실 규칙을 따르며, evidence 에 인용을 단다.
- 흐름도와 본문의 숫자·상태(완료/진행)가 다르면 본문 원문을 따르고 needs_check 에 적는다.
- Word 출력에는 mermaid 를 이미지로 바꿔야 한다는 안내를 reply 에 남긴다.

### 5. 프로젝트 합치기·나누기
- 같은 흐름의 업무(예: 반기별 표준 모델 개선 + 피처 개선 버전 + 학습데이터 생성)는 사람이 요청하거나 승인했을 때만 합친다.
- 합칠 때는 하위 항목마다 원래 이름과 원래 기간을 남긴다.
- 합친 근거(같은 모델 라인인지 등)는 needs_check 에 적는다.

### 6. 받지 못한 참고 파일
- 사람이 말한 파일(예: 'md 경력서')이 근거 자료에 없으면 표준 형식으로 대신하지 않는다. 먼저 파일을 요청한다.
- 시간상 먼저 써야 하면 그 사실을 reply 첫 줄에 적는다.

### 7. 원문 오탈자
- 본문에서는 명백한 오탈자를 고쳐 쓸 수 있다. (예: 정재 → 정제, 기관 이름 끝 글자 오타)
- evidence quote 에는 원문을 그대로 두고, 고친 내용을 needs_check 에 적는다.

### 8. 공개 저장소 업로드 (GitHub)
- 근거 문서에 '개인용 사본 · 커밋하지 않음 · 회사 업무 포함' 표시가 있으면 공개용 결과물을 따로 만든다.
- 공개용에서 가릴 후보는 고객사·기관명, 내부 제품·버전명, 내부 성능 수치, 내부 위험 항목 번호다.
- 무엇을 가릴지는 사람이 정한다. 모델은 후보 목록만 needs_check 에 적는다.
- API 키·경로·계정 정보는 결과물에 넣지 않는다.

### 9. 질문으로 되묻기
- 형식·분류·그림처럼 결과 모양을 크게 바꾸는 판단은 먼저 혼자 정하지 않는다.
- 쓰기 전에 사람에게 1~3개 질문으로 확인한다.
