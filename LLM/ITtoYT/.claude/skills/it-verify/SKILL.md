# IT 개념 검증 (it-verify)

## 이 스킬이 존재하는 이유

IT 개념은 **버전과 시점에 따라 사실이 바뀐다.** "HTTP/2는 TCP 기반" 같은 문장은 맞지만 "HTTP/3도 TCP" 는 틀리고, 벤치마크 수치는 측정 조건 없이는 무의미하다. 게다가 한국어 기술 블로그에는 오래된 정보나 오역이 그대로 복제돼 퍼져 있다.

모델 기억에서 뽑은 설명은 그럴듯하지만 틀린 지점을 반드시 포함한다. 그 상태로 영상을 만들면 틀린 정보가 조회수만큼 증폭된다. 그래서 **주장을 쪼개고, 주장마다 출처를 붙이고, 출처 등급을 매긴다.**

## 워크플로

### 1. 스코프 확정
개념명을 받으면 먼저 다룰 범위를 한 문장으로 정한다. 범위가 넓으면(예: "쿠버네티스") 영상 한 편 분량으로 좁힌다 — 넓은 주제는 검증도 얕아지고 영상도 지루해진다.
- 대상 개념 / 대상 버전·시점 / 다루지 않을 것 을 명시한다.

### 2. 주장 분해
설명하려는 내용을 **검증 가능한 단문 주장**으로 6~15개 쪼갠다. "빠르다" 는 주장이 아니다. "동일 조건에서 X가 Y보다 p95 레이턴시가 낮다" 가 주장이다.

주장 유형별로 최소 1개씩은 확보한다:
- **정의형**: 이 기술이 무엇인가
- **메커니즘형**: 내부적으로 어떻게 동작하는가 (영상의 핵심 — 여기가 부실하면 뻔한 콘텐츠가 된다)
- **비교형**: 무엇을 대체하거나 무엇과 다른가
- **한계형**: 언제 쓰면 안 되는가 (대부분의 콘텐츠가 빼먹는 부분이라 차별점이 된다)
- **수치형**: 벤치마크·제한값·기본값

### 3. 출처 수집
WebSearch로 후보를 찾고 **WebFetch로 실제 본문을 읽는다.** 검색 결과 스니펫만 보고 확정하지 않는다 — 스니펫은 맥락이 잘려서 반대 의미로 읽히는 일이 흔하다.

출처 우선순위:
1. **1차**: RFC/IETF, W3C, 표준 스펙, 벤더 공식 문서, 논문, 실제 소스코드·커밋·릴리스 노트
2. **2차**: 해당 기술 메인테이너·엔지니어링 블로그, 컨퍼런스 발표
3. **3차**: 일반 기술 블로그, 요약 사이트 — **근거로 쓰지 말고 "이런 통설이 있다" 는 증거로만 쓴다**

각 주장에 **서로 독립적인 출처 2개 이상**을 붙인다. 같은 원문을 인용한 두 블로그는 독립 출처가 아니다.

### 4. 등급 판정
| 등급 | 조건 |
|---|---|
| `확정` | 1차 출처로 직접 확인, 상충 없음 |
| `통설` | 2차 출처 다수 일치, 1차 출처 미확인 |
| `논쟁` | 신뢰할 출처끼리 서로 다르게 말함 |
| `미확인` | 근거를 찾지 못함 |

`논쟁`은 숨기지 말고 상충 내용을 양쪽 다 적는다. 콘텐츠에서 가장 재미있는 지점이 보통 여기다.
`미확인`은 삭제하지 말고 남긴다. 다음 단계에서 "영상에 넣지 말 것" 목록이 된다.

### 5. 흔한 오해 수집
검색 중 마주친 **틀렸는데 널리 퍼진 설명**을 따로 모은다. 한국어 검색을 한 번은 반드시 돌려서 국내에 퍼진 오해를 확인한다(오역·구버전 정보가 많다).

이건 부수 작업이 아니라 핵심 산출물이다. "사실은 아닙니다" 는 영상 훅으로 가장 강력하고, 오해 목록이 곧 short 소재가 된다.

### 6. 팩트시트 작성
`IT 개념/<slug>/00-research.md` 에 저장한다. `<slug>` 는 영문 kebab-case (예: `quic-http3`, `ebpf-basics`) — 이후 자동화 단계에서 경로를 다루기 쉽게 하려는 것이다.

## 출력 템플릿

```markdown
# <개념 한글명> (<영문명>)

- slug: <kebab-case>
- 검증일: YYYY-MM-DD
- 대상 버전/시점: <예: HTTP/3 RFC 9114, 2022 확정 기준>
- 다루는 범위: <한 문장>
- 다루지 않음: <한 문장>

## 한 줄 정의
<비유 없이, 정확하게 한 문장>

## 검증된 주장

### C1. <주장 한 문장> `확정`
- 근거: <출처가 실제로 말한 내용을 요약. 추측 금지>
- 출처: [제목](URL) / [제목](URL)

### C2. ...

## 동작 원리
<C 번호를 인용하며 흐름 순서대로. 여기서 새로운 사실을 만들지 않는다>

## 흔한 오해
### M1. "<퍼져 있는 틀린 설명>"
- 실제: <올바른 설명> (C3 근거)
- 왜 퍼졌나: <추정이면 추정이라고 표기>

## 수치·제한값
| 항목 | 값 | 측정/정의 조건 | 출처 |
|---|---|---|---|

## 논쟁 지점
<출처 간 상충. 양쪽 입장과 각 출처>

## 영상에 쓰지 말 것
- <미확인 주장, 그리고 왜 위험한지>

## 출처 목록
1. [제목](URL) — 등급(1차/2차/3차), 발행·갱신 시점
```

## 자주 하는 실수

- **비유를 사실처럼 적는 것**: 팩트시트에는 비유를 넣지 않는다. 비유는 다음 단계(nlm-pack)에서 만든다. 여기서 비유가 섞이면 검증 대상과 수사(修辞)가 구분되지 않는다.
- **날짜 없는 출처를 신뢰하는 것**: IT 문서는 갱신 시점이 곧 유효성이다. 시점을 못 찾으면 그렇게 표기한다.
- **주장 수를 채우려고 뻔한 정의만 늘리는 것**: 메커니즘형·한계형이 부족한 팩트시트는 그 다음 단계 전체를 얕게 만든다.
- **`확정`을 남발하는 것**: 1차 출처를 직접 읽지 않았으면 `통설`이다. 이 구분이 무너지면 등급 자체가 무의미해진다.

## 끝낸 뒤

검증 결과를 3~5줄로 사용자에게 요약한다. 특히 **모델 기억과 달랐던 지점**과 `논쟁`·`미확인` 항목을 반드시 언급한다. 그게 사용자가 판단해야 할 부분이다.

이어서 영상 소스팩이 필요하면 `nlm-pack` 스킬로 넘어간다.
